# Architecture

Avala is a desktop harness for coding agents, written in C# on .NET 10 with Avalonia. It runs each agent in its own git worktree, answers its requests through explicit policies, judges its work by the repository's own checks and accounts for every token it spends. This page is the big picture: what the parts are and how they fit together.

## A modular monolith of plugins

Avala ships as one process, but the process knows almost nothing about what it runs. The host is an Avalonia application, a composition root and a plugin loader: it scans its `plugins` folder, instantiates every `IPlugin` it finds and lets each one register its services, handlers and views. The host references no module.

```
src/
  Avala.Sdk               contracts every plugin builds on, no UI framework
  Avala.Sdk.UI            contracts for plugin views, the view registry
  Avala.Runtime           the event bus, the process runner, logs, appearance
  Avala.Shell             the main window's view models and regions
  Avala.Host              the application, composition root and plugin loader
  Shared/                 components, storage and command-line reading every module may use
  Modules/<Module>/
    Avala.<Module>             the module's core: domain, use cases, infrastructure, view models
    Avala.<Module>.UI          its views and its plugin entry
    Avala.<Module>.Contracts   optional public contracts other modules may use
```

The modules are Agents, Jobs, Workspaces, Verification, Permissions, Supervision, Budgets, Resources, Observability, Canvas, Autopilot, Delegation, Handoffs, Triggers, Notifications, Contests, Transcripts, Recording, Preview, the Workbench, the canvas renderers (Rendering and Mermaid), the Simulator and the Claude Code provider.

- **A module depends only on the SDK, its own projects and other modules' `Contracts`.** Everything else in a module is `internal`; its single public type outside its contracts is its plugin entry.
- **Folders are named after what the code does**, such as `Submission`, `TurnChecks` or `Storage`, never after layers. The layers still exist, Domain, Application, Infrastructure and ViewModels, and a single layer map in the architecture tests assigns every namespace to one, so dependencies keep pointing inward.
- **All plugins share one load context**, so a contract has one type identity for every module: the `IAgentProvider` the simulator implements is the one Agents asks for.

A new capability, such as an issue tracker or another way to isolate work, arrives as a new module, without touching the core. It talks to the rest of Avala in three ways only:

| Mechanism | Use it to |
| --- | --- |
| Integration events on the bus | React to what happened |
| Contracts injected through dependency injection | Ask for an answer or an action |
| Extension points the core defines and plugins implement | Let the core use something it does not know, such as `IAgentProvider`, `ICompletionGate`, `IApprovalStrategy`, `IJobAdmission` or Autopilot's `IJobSource` |

## Domain

Each module's domain is plain, deterministic C#: no I/O, no async methods, no exceptions. Aggregates are sealed classes with factory methods and no public setters; every public operation returns a `Result<TEvent, TError>`, absence is an `Option<T>` rather than `null`, and each module that can reject an operation has one error enum. Lifecycles such as a job's are state machines built on Stateless, and their [diagrams](diagrams/) are generated from the code.

## The event bus

Modules learn what happened through integration events on an in-process bus, implemented in `Avala.Runtime` over `System.Threading.Channels`. Publishing never blocks: one router reads events in publishing order and posts each to the mailbox of every handler of its type. Each handler has its own mailbox and reader loop, so it sees its events one at a time, in order, and keeps plain state without locks; a slow or failing handler delays or fails only itself. Events state facts: nothing asks a question over the bus and waits for a reply, since a contract makes that dependency explicit.

The same discipline holds everywhere: concurrency between components goes through the bus or channels only, and nothing waits on time where it could await the event that states the thing happened.

The runtime starts on the thread pool, whoever starts it: the router and the startup tasks never run on the UI thread, so only handlers that change what the interface shows marshal to it, through `IUiDispatcher`. Startup runs in stages. In `Open`, every module opens and migrates its own database, all at once since no two share a file; then the `Restore` tasks run one after another, then `Recovery`, and `StartupCompleted` follows.

Nothing Avala starts outlives it. Stopping the application disposes the process runner, which cancels every process it still runs, kills its tree and returns only once each has exited, and refuses to start another; a read nobody awaits, such as the inspector checking a repository's remote, therefore never keeps a repository's folder in use after Avala stops.

## Agents and the provider contract

`Avala.Agents.Contracts` is the only thing a provider plugin depends on. A provider implements `IAgentProvider`: it starts an `IAgentSession` that streams agnostic events, such as turns, messages, reasoning, file edits, commands, permission requests, forms, usage and limits, and accepts turns, permission decisions, form answers and interruptions. The Agents module checks every event of every turn against one `Turn` aggregate, so a provider translates a protocol and never re-derives lifecycle rules.

Providers do not declare a fixed list of flags. Each capability is a **component**: a small sealed record such as `Interruptible`, `Resumable`, `AcceptsTools`, `AsksForms` or `ReportsLimits` with the windows it reports, attached to a `CapabilitySet` per connection. The core's systems query the components they know and ignore the rest, so behavior depends on declared capabilities, never on a provider's name. A plugin may define components of its own.

Sessions open on **connections**: one harness with one account, credential and configuration, several per harness if you like. Avala offers its own harness tools, such as the canvas, delegation and follow-ups, to every provider that accepts them, and each harness adapts to that offer through its plugin. A conformance kit checks every provider against the contract.

Claude Code is the first real provider: it runs the `claude` CLI in its streaming JSON mode and serves Avala's permission prompt and harness tools from an MCP server inside the session. The CLI hides MCP tools behind its tool search until the model looks for them, so a model asked for a chart never saw the canvas and wrote an HTML page instead; when a session is offered the canvas, the plugin lists it to load up front (`_meta` `anthropic/alwaysLoad`) and appends a short system prompt that asks the model to show anything visual on it, in the formats the canvas offers, instead of writing a page or opening a browser. The canvas plays SVG animations written in SMIL (`<animate>`, `<animateTransform>`, `<animateMotion>`, `<set>`), which Svg.Skia evaluates; it runs no CSS keyframes and no script, and nothing on it responds to input. The canvas tool's description and the prompt say so, and send anything that must respond to input, such as an interactive chart, a three.js scene or an app, to a page: when the Preview plugin offers its `PreviewOffer` to a provider that declares `AcceptsPreview`, as Claude Code does, the prompt asks for a page kept in the worktree with its libraries vendored, served on 127.0.0.1 at `$AVALA_PORT` from the ports `$AVALA_PORTS`, and its URL told to the person, since Avala shows it in its Preview pane beside the conversation, and never a browser opened or a screenshot taken; without that offer, it asks for a self-contained HTML file, whose path the person opens from its line. An SVG takes the size of its `viewBox`, which the sanitizer writes as its width and height, and is laid out at that size inside a uniform fit that scales it up or down to the canvas's width, up to the card's height, so a still and an animated drawing of the same `viewBox` take the same space and the card's height follows the drawing; the animating control composes its layers at the drawing's own size, where a `viewBox` larger than the width and height used to crop them. Each SVG is parsed off the UI thread, once per content, and its card shows an empty area of the drawing's size until it is drawn, while a new version of a canvas keeps the previous drawing on screen until the new one is drawn (`CanvasPresenter.IsDrawing` and its `Drawn` event). A still drawing stays a plain image; an animated one is drawn by Svg.Skia's animating control, which composes only the layers that move, and it plays only while it is on screen: it pauses when the drawing is detached, scrolled out of view, hidden or its window minimized, and stops when a finite animation has ended. It never takes the pointer or the wheel, so scrolling over it scrolls the conversation. With reduced motion it shows where its animations settle instead of their first frame, and a play button on hover plays it once.

## The simulator and recordings

Everything Avala does is proven through the **simulator**, a provider plugin that plays scripted Claude Code sessions through the same public contracts as a real provider, without a model and without tokens. Its scenarios are declarative data: reasoning, streamed replies, real file edits, commands with real child processes, permission requests, forms, plan approvals, usage and limits, canvases, delegation and resumed conversations. It also registers a second simulated harness, so behavior across harnesses runs without a real one.

The **Recording** plugin decorates every provider and, when enabled, records each session as a file the simulator replays. Recordings committed under `tests/recordings` with their expected outcomes are regression tests, and the screenshots in the README are taken from the real application driven headless by the simulator.

## The trust layer

Avala's purpose is agents you can trust without watching. Four modules carry that, each a plugin built on the extension points above.

**Verification.** A job is done only when the checks its repository declares pass in its worktree. Verification registers a completion gate that runs those checks after every finished turn and keeps the evidence of every attempt; the review shows that verdict first.

**Permissions.** Every permission request and every question an agent asks goes through an explicit policy, built-in guards and defaults around the rules the repository commits, at the level of autonomy the job allows. Sessions always open asking before every edit and command, so nothing bypasses the policy. Every process of a job gets `TMPDIR`, `TEMP` and `TMP` pointing at a scratch folder of its worktree under the data folder's `temp` folder, created when the worktree's first process tree opens and removed when the job ends; the policy counts a write resolved inside it as inside the workspace, so temporary files never wait for a person or get denied under autonomous, and they never show in the job's diff. Every decision is audited with the reason it was made, including the ones left to a person. A line whose every part only reads inside the worktree, such as `ls`, `grep`, `git status` or `git log` without a redirection to a file, runs without asking, audited as "read-only allowed", unless a repository rule says otherwise. A person answers a request once, always for its program in this job (one rule per program a chained line still needs, with any arguments; for the web its host, for a tool its name), or with everything in this job, which runs the rest of the job at autonomous with the guards still first; a repository that declares itself supervised keeps that ceiling, and one without a declared level lets a person raise its job. Under autonomous, a request the policy denies leaves a card in the conversation, Denied with what was asked, that never holds the turn; when a job rule could allow it, Allow and retry keeps that rule for the job through `IDeniedRequests`, records it as a person's answer and tells the agent, the way the composer sends a message, that it may retry, while a denial a guard keeps for a person says so and offers nothing.

**Supervision.** An agent that goes silent is noticed and its job held, with the facts that were measured, instead of hanging forever. A session that dies is caught by Jobs and held as lost.

**Budgets.** Caps on cost, tokens, memory and provider limits stop a job before it overspends; a child job's budget is carved out of its parent's, and the machine admits only as many running jobs as its limit allows. Every intervention is recorded.

Around them, **Resources** samples the processes, ports and disk every job uses, reaps what a session leaves behind, leases ports per worktree and reclaims old worktrees; **Observability** keeps usage, cost and limits per provider, account, connection, session and job; **Autopilot** runs a backlog unattended and approves a job automatically only on clean evidence; **Delegation** lets an orchestrating agent hand work to child jobs that are governed and verified like any other; and **Triggers** starts work unattended, on a schedule, on a signed webhook received on a loopback port only, or on a forge event such as an issue labeled, a command in a comment, failing checks on a branch or a review requested, as ordinary jobs that never exceed their repository's autonomy. Forge events are polled through the forge plugins, so a laptop needs no public endpoint; the first poll only records where the forge stands, each event is judged against the trigger's filter and an explicit list of authors checked against who acted, fires at most once and moves the stored cursor only once its fire is recorded, and a forge's own signed webhook only asks for a poll at once. A forge trigger's instruction is filled from its event, so it is never run by hand: Check now on the Triggers page polls it at once instead. Avala never opens a public port: receiving webhooks from the internet takes a tunnel of your own, such as Tailscale Funnel.

**Repositories** come from a person, never from an agent. Workspaces owns git: it makes a folder a repository, creates a new one, clones an address into a new folder under a chosen parent and publishes a repository to a remote, always through the process runner, with terminal prompts turned off, so a refused credential is reported as unauthorized instead of waiting on a prompt nobody sees. A failed or cancelled clone removes only the folder Avala made for it, and never follows a link inside it. Forges creates the repository on a forge connection of `forges.json`, for the account of its token, through an optional capability a forge plugin implements (`IForgeRepositories`): GitHub, Gitea and Forgejo through their APIs, and the simulated forge as a bare remote under the data folder. Avala then adds it as `origin`, over HTTPS when git has a credential helper for that host and over SSH otherwise, and pushes the current branch with its upstream, using the person's own git credentials; Avala never holds a token for git. Publishing again when `origin` already is that repository only pushes, so a push refused for credentials can be retried once they are fixed. Publishing and cloning are commands of the interface only: no agent is offered them as a tool.

**Accounts** are the harness connections and the forge connections of `forges.json`, shown together first in Settings, above the repository rules. Forges writes `forges.json` through `IForgeConnections`, one write at a time through a file moved into place, keeping its poll interval and every other entry. It also finds the accounts this computer already signs in with: a forge plugin may declare `IForgeLogins`, the command that lists its command-line logins and how to read them, such as `gh auth status` or `tea login list`, and the names of its token variables. The core runs those commands through the process runner and only checks whether a token variable is set: it records names and references, never a value, so a found account is added with one click and nothing is written without the person. A login one tool holds for two forges, such as tea for Gitea and Forgejo, is told apart by probing the host. `ISourceControlAccounts` names who each account signs in as through the optional `IForgeAccounts`, and lists an account's repositories, most recently changed first, through `IForgeRepositories`, with the address to clone them chosen as publishing chooses it. Workspaces keeps the projects folder clones go into, the first of `~/Projects`, `~/projects`, `~/code`, `~/src`, `~/dev` and `~/source/repos` that exists until a person chooses one, asked for once and kept in `workspaces.json`. Harness logins are discovered again on request, so one made while Avala runs appears without a restart.

**Contests** runs one request as several candidate jobs and keeps the best by its evidence, never by an agent's word. Each candidate is an ordinary job, in its own worktree with its own session, retries and checks, on the connection a job would take now or spread across the usable connections when asked, and its budget is an even share of the per-job caps, carved by Budgets. Once every candidate has settled, the verdict requires a passing verification, disqualifies a run that edited a rule file or rewrote its checks, and ranks the rest by fewest evidence exceptions, fewest attempts, smallest diff, lowest cost and earliest finish; when nobody passed, the contest waits for you with every candidate shown. Approving any candidate picks it and discards the others, whose worktrees are reclaimed as usual. Jobs knows nothing of contests: Contests submits and discards jobs through their contracts, keeps its contests in `contests.db`, and recovers them at startup from the job catalog. The `bestOf` section of `.avala/jobs.json` sets how many candidates a job starts with and the most a contest may have, and an answer given "in this contest" to a candidate's permission request goes to every candidate.

**Notifications** tells your phone when a job needs you while you are away from the Avala window: a decision left to you, a held job, a budget or limit hold, a failed job or an ended loop, and a job ready for review if you ask for it. It only listens to other modules' events; only the Workbench reads its contracts, to show its settings. A notice waits thirty seconds so several become one message, is never sent if you answer in the app first, and is sent only once nobody has touched the Avala window for two minutes, a signal the host offers every plugin through the SDK's `IPresence`. It goes to [ntfy](https://ntfy.sh), on a private random topic by default or a server of your own, with an emoji tag per kind that ntfy shows as an icon, or to a webhook of your own, signed like a trigger webhook. What is sent is minimal by default, the event, the repository, the job's title and a count, and the tool and target are added only if you choose detail, through the same redaction as the log. One notice per job and kind until it is resolved, even across a restart, at most twenty an hour, urgent ones through your quiet hours and the rest in one digest after, retried three times before it is reported failed. `notifications.json` in the data folder holds the settings and names the environment variables of any token or secret, never the secret itself; Settings shows exactly what is sent and sends a test.

## Usage statistics

A packaged release counts installs and daily active installs through [Aptabase](https://aptabase.com), and nothing else. `UsageTelemetry` in the runtime, beside the update check and behind the SDK's `ITelemetry`, sends `installed` once ever and `active` at most once per local day, each with the version, the operating system and its architecture under a random install ID kept in `telemetry.json`. It runs in the background at startup and at local midnight, never blocks the window and retries what failed at the next start. Only a build packaged with the `AvalaTelemetryKey` property can send, and `DO_NOT_TRACK=1`, `AVALA_TELEMETRY=0` or the person's choice turn it off; the Workbench shows a one-time notice in the sidebar's footer and a section in Settings, About, with the status, the install ID and exactly what is sent. [Releasing](release.md#usage-statistics) has the details.

## Jobs without a repository

Every job runs against a git repository, so a job started without one gets a repository of its own. The welcome's composer, No repository in New job's repository pop-up, which is its choice when no job ran yet or the last job ran without one, or Ctrl/⌘+Shift+Enter in its instruction, asks Workspaces' `IScratchRepositories` for a scratch repository and submits the job there as any other: its own worktree, the permissions of a repository that declares none, the budgets, verification and review. A scratch repository lives in the data folder's `scratch` folder, named after the local day, the first four plain words of the instruction and a short random id, such as `scratch/2026-10-12-sketch-a-csv-parser-3f9a1c`, with a fresh id when a name is taken. Its first commit holds only `.avala/jobs.json` declaring `merge`, so approving a job lands its work on the scratch repository's branch where Open folder finds it; it declares no checks, so verification says so and the review still shows the diff. When git knows no identity, that first commit is made under Avala's name, as Avala's own checkpoints and merges are, so a scratch job works out of the box; making or initializing a repository of your own still refuses without one. Scratch repositories are never suggested as a job's repository, their jobs carry a Scratch tag in the sidebar, and the inspector's worktree section names the folder and opens it. They hold work, so Avala keeps them and never deletes anything there; keeping one as a regular repository means moving it out of `scratch` yourself.

## Persistence

Each module owns its data in its own SQLite database under the data folder, through EF Core with migrations, and no module reads another module's data. Every fact a screen presents as part of a job's record, such as the job, its usage, its evidence, its audit and its conversation, survives a restart; what belongs to a live session, such as a pending permission, dies with it. Database work never runs on the UI thread, and an architecture test checks that every module's model matches its latest migration.

## The Workbench

The Workbench is the module of the user interface, built on other modules' contracts only. It follows MVVM, view model first: view models live in the module's core assembly and reference no UI framework, and views live in its `.UI` assembly, so another UI technology means replacing the `.UI` assemblies and nothing else. A view only binds, with compiled bindings, theme resources and commands, and binds a selection through `Kept.Selection` so a view torn down cannot clear it, and takes every shortcut and the label its tooltip shows from `Hotkeys`, which presses ⌘ on macOS and Ctrl elsewhere; the view registry picks the view for each view model. The main window is drawn as named **regions**, an idea taken from Prism: a page declares its regions, plugins register view models into them, and a region's context, such as the selected job, reaches every component in it, so a page never knows the components other modules contribute. Components that live apart talk through small UI messages over an injected messenger. The jobs page shows a welcome whenever no job is selected: one composer that starts a scratch job, with a chip inside it that names the connection Auto would pick now and why, and opens a menu of Auto and each usable connection with its usage, then the model and effort of a chosen connection, a choice kept for the next chat until Avala restarts; cards that open a folder, clone or make a repository, and a chip per account whose status dot turns amber with its one fix; once jobs exist, only the question and the composer stay. The conversation's composer shows the same chip, one view model and view (`HarnessChoiceViewModel`) fed by the welcome's `WelcomeHarness` and by each conversation's `JobHarness`: it reads the job's connection, model and effort, the chosen ones or else the ones its harness reported, and its menu lists the job's connection, then "Continue on" each other usable connection, then the model and effort. A job that is held or awaits review, on a harness that resumes conversations and offers models, takes another model or effort through `IJobs.ChooseModelAsync`: Jobs stores it with the job, stops the idle session, and the next message resumes the conversation in a new session with it. A held job continues on another connection through Handoffs' `IHandoffRequests`, the same handoff and brief as at a usage limit, recorded as the person's choice. While the agent works, both stay visible and read only. Every view model has a design-time implementation, so every view renders in the designer, and every component has scripted acceptance tests that drive it as a user would, headless.

The conversation copies through `IClipboard`, a port of the SDK that the shared components implement with the platform's clipboard, so a view model copies a reply or a prompt without knowing the UI framework, and tests use a fake. Presentation that is only about time stays in the views: the checkmark a copy shows for a moment and the elapsed time of the working row and of a running job's sidebar row tick on the dispatcher, from a start time the view model hands down, and the views read their clock from an inherited `ElapsedText.Clock`, so a test sets a fake clock instead of waiting. The send key is part of the appearance kept in `appearance.json`: Enter sends and Shift+Enter adds a line, or Command (Control elsewhere) with Enter sends when chosen in Settings; the composer reads the choice at the moment a key is pressed, so a change applies to every open conversation at once.

A code block in a reply is colored by the TextMate grammar its fence names, through `MarkView.Avalonia.SyntaxHighlighting`'s TextMateSharp grammars: each token's scope is mapped to a small set of roles, keyword, string, number, type, function and comment, drawn with the theme's `Syntax…Brush` tokens, so code follows the app's palette in light and dark instead of an editor theme. The job's more menu copies the conversation as Markdown or exports it to a file: `TranscriptMarkdown` writes it in the Workbench's application layer from the same `Transcript` the conversation shows, prompts and replies as they are, each tool as one line with its output in a fenced block only when it is expanded on screen, and reasoning left out; the file is chosen and written through `IFileSaver`, a port of the SDK the shared components implement with the platform's save dialog. A file edit's line opens the file's hunks against the job's base in a popover, through `WorkedFiles`, which reads the diff of the job's workspace and is drawn with the review's `HunkView`; the file is the path its title names after `Write ` or `Edit `, the shape every harness gives a file edit's title, and a title cut short names no file. A written image, SVG or HTML file offers a preview on its line: `WorkedFiles` finds the file in the job's worktree, or in its repository once the worktree is gone, through `IWorkingFiles`, which never reads outside the folder it is given; an image is decoded by the view, an SVG is handed to the canvas renderers as a `CanvasRendering`, so it is sanitized and drawn exactly like an SVG canvas, and a small one also shows as a thumbnail under its line; a page is opened in the person's browser through `ILinkOpener`, since Avala draws no HTML.

A job's page or app shows in a **preview** beside its conversation, from the Preview plugin. It watches every sample of Resources: a process of a job's tree listening on a port offers that job's preview, as `PreviewAvailable`, labelled unleased when the port is outside the job's lease, and the preview is withdrawn, as `PreviewGone`, when the server stops or the job ends. Run, in the job's header, starts the worktree's `dev` script, or `start`, with the package manager its lock file names, in a process tree of the worktree whose lease reaches it as `AVALA_PORT`, `PORT` and `HOST=127.0.0.1`, and stops with the job; a worktree with no script but an `index.html` has it served instead. No page loads straight from the agent's server: every preview goes through a loopback gateway on a lease of the job's own, a proxy that bridges the server's WebSockets for hot reload, or a static server confined to the worktree, and both add a Content-Security-Policy that keeps other origins out, so a page fetches nothing from the internet until Allow network is on, for that job until Avala restarts. A top-level navigation is checked against an allow-list in the domain, the loopback ports of the job's lease, its listeners and its gateways, and files that resolve inside its worktree, links followed; anything else, a new window included, is cancelled and offered to the browser with one click. The page is drawn by the operating system's web view through `Avalonia.Controls.WebView` behind an `IWebSurface` port of the Preview contracts, with private storage and no developer tools: embedded where the platform embeds it (WebView2, WKWebView, WPE WebKit), in a window of its own where it only offers one (WebKitGTK under native Wayland, which only embeds through X11), and otherwise the pane says so and offers the browser. The Workbench draws the job's page as regions, `WorkbenchRegions`, beside the shell's: the job's header holds the Running chip, whose dot pings once as it appears, and Run, the conversation a chip of its own while the pane is closed, and the preview sits right of the conversation at 45% of it by default, resized by dragging its edge between 25% and 70%, remembered in `layout.json`, reset by a double-click, and hidden in focus mode. A server that a selected job starts opens the pane by itself, once for that job and port, so a person who closes it is not interrupted again by the same server, and a server already running when its job is selected waits for the chip. A link in a reply to a loopback address that one of the selected job's servers answers, on its lease or a port it listens on, opens in the pane instead of the browser: the Workbench sends the SDK's `LocalPageRequested` UI message and opens the browser only when no pane shows the page.

Motion is opt-in. An element animates only through `Motion.Enter`, `Motion.Loop` and `Motion.When`, which check reduced motion themselves; a loop runs only while its element and every ancestor are visible, and a fold's one-shot animations finish even while hidden, since a paused animation keeps Avalonia's 60 Hz animation clock awake; the theme holds no style that matches every visual, because Avalonia attaches such a style to each visual it builds and every screen paid for it. Pages and the selected job's conversation appear on a **stage**: the click's own change, such as the sidebar highlight and the job's header, paints first; the new view is built at background priority while the current one stays on screen, and once the new view is laid out the two cross-fade in 240 ms with a slight rise and scale on a settling curve, started on a fresh frame so a slow build never eats the fade; under reduced motion the swap is instant. Page views stay alive between visits and the four most recently viewed conversations keep their view models and views, so switching back is instant, and entrances inside content being laid out hold still so only later arrivals move. The conversation is virtualized by a timeline panel: it opens at its newest screenful without building its first entries, builds older entries as the reader scrolls up, where they hold still, and a newly opened conversation fills its entries in one change. The panel remembers each entry's measured height for the column's width, estimates an entry not yet built from the heights measured for its kind and from its text length, which messages, prompts and interjections give through `ITextSized`, and builds the screenful above and below at idle priority, so the scrollbar holds steady and a first scroll finds its entries ready; what the reader sees stays in place while entries above settle. While a reply streams, each settled block becomes its own Markdown view and is never parsed or drawn again, only the growing last block is; Select All and Copy span the blocks, and once the reply ends it becomes one document again, so a drag selection can cross its blocks. A conversation shares one set of Markdown styles instead of loading them per message, and each SVG canvas is parsed once. Each inspector section shows as soon as its own facts are read, with a quiet bar that appears only if the read takes longer than 150 ms, and pages update their rows in place, as the Usage page's connections do, instead of rebuilding them on every refresh. The window keeps its layout in `layout.json` next to `appearance.json`: the sidebar collapses from the window controls or Ctrl/⌘+\ and below 1,000 px, and its width, 260 px by default, follows a drag of its edge between 200 and 400 px, is remembered once the drag ends and returns to 260 px on a double-click; rows that would clip shorten or drop their secondary facts through container queries. Focus mode is only a shortcut, Ctrl/⌘+Shift+F: it hides the sidebar, the inspector, the window controls and the page and job headers, widens the reading column as Wide does and shows a hint that fades out; Esc or the same shortcut leaves it. The reading column grows with the window, further when Appearance sets the reading width to Wide.

Personal details are hidden by default, so a screen can be recorded or shared as it is. A view model never exposes a person's email, login, account name, organization id or home-folder path as plain text: it exposes a `Personal` value of the shared components, which knows its kind and masks it by one rule per kind (`r•••••@g••••.com`, `oc•••••`, `D••••• M•••••`, `3f2a•••••`, `~/…`), or a `PersonalPhrase` for a sentence that holds one. Views show them through `PersonalDetails.Text`, and free text that may mention them, such as a tool line, a permission target or a repository path, through `PersonalDetails.Scrubbed`. A notice or error that names one does the same: a sentence that holds a known folder or login, such as an unopened log folder, a created or cloned repository or a published origin, is a `PersonalPhrase`, and one that may hold a path, such as a file the platform would not open or what a command writes, is scrubbed; both follow the inherited `PersonalDetails.AreHidden` of the window, which the appearance sets, so a change applies live everywhere, popups included. The switch is "Hide personal details" in Settings, Appearance, kept in `appearance.json` as `hidePersonalDetails`, with an eye in the Accounts header for the same setting; a copied or exported conversation is scrubbed the same way while it is on. Connection names are chosen by the person and stay as they are. An architecture rule rejects a view model interface whose text property is named after an email, a login, an account, an organization, a user name or an owner.

## Quality gates

The rules are code, and a failing rule explains itself.

- **Architecture tests** in `tests/Avala.ArchitectureTests` enforce the module boundaries, the layer map, the domain's purity, the view rules, the absence of comments, type and component size limits, the concurrency and timing rules, and that every script is C#. Each rule runs against the production code, a compliant fixture module and a violating fixture module, so it can never pass vacuously.
- **Analyzers** run on every project as errors: banned symbols for blocking calls, timed waits and coordination primitives, the threading analyzers, SonarAnalyzer.CSharp and the .NET code metrics rules, with their limits in `SonarLint.xml` and `CodeMetricsConfig.txt`.
- **CI** builds and tests on Linux, Windows and macOS on every push to `main` and every pull request, using only `dotnet` steps.

### Quality metrics

On every push to `main` and every pull request, CI also measures coverage, code metrics, technical debt and lines of code with open-source tools and no external service, and shows them in the run summary.

- **Coverage** comes from the unit tests, listed in `Avala.UnitTests.slnf`, collected on every operating system and merged, so platform-specific code counts where it runs.
- **Code metrics** are the maintainability index, cyclomatic complexity, class coupling and lines of every production assembly, type and member, computed by `scripts/code-metrics.cs`.
- **Lines of code** are physical lines of C# outside tests and generated code. They are compared with [T3 Code](https://github.com/pingdotgg/t3code), about 907,000 lines of non-test TypeScript at commit `a4c9494b0`, as a fixed yardstick: Avala aims for a better product in no more than 15% of that.

### Technical debt grade

`scripts/metrics.cs` rates four indicators from A to E, and the grade is the worst of the four:

| Indicator | A | B | C | D | E |
| --- | --- | --- | --- | --- | --- |
| Line coverage of the unit tests | ≥ 80% | ≥ 70% | ≥ 60% | ≥ 50% | < 50% |
| Mean maintainability index of the production methods | ≥ 80 | ≥ 70 | ≥ 60 | ≥ 50 | < 50 |
| Highest cyclomatic complexity of a production method | ≤ 10 | ≤ 15 | ≤ 20 | ≤ 25 | > 25 |
| Risk hotspots (CRAP score above 30) per 1,000 methods | ≤ 1 | ≤ 5 | ≤ 10 | ≤ 20 | > 20 |

On a push to `main`, the badges in the README are drawn by the same script and published on the `badges` branch.

## Platform workarounds

Each workaround answers a problem that was reproduced and measured, and goes when its cause is fixed.

| Workaround | Problem | Measured | Goes when |
| --- | --- | --- | --- |
| Wayland backend (`DesktopSession`) | Avalonia draws through X11 on Linux by default. Under a Wayland compositor at a fractional scale (1.6 on Hyprland), XWayland renders the window at scale 1 and the compositor stretches it, so text is blurry. The X11 alternative (`xwayland:force_zero_scaling` with Avalonia's own scale) misplaces clicks. On a Linux session with `WAYLAND_DISPLAY`, the host uses Avalonia's Wayland backend (falling back to X11), drawn at the screen's own scale; `AVALA_X11=1` forces X11. Windows, macOS, X11 sessions and the headless `--smoke` run are untouched. | 2026-10-12, Hyprland at 1.6: blurry over XWayland, sharp over Wayland | Avalonia uses Wayland by default |
| WebKitGTK without its DMA-BUF renderer (`NativeSurfaces`) | Under native Wayland, WebKitGTK only opens the preview in a window of its own through XWayland, and its DMA-BUF renderer fails to allocate its GBM buffers there ("Failed to create GBM buffer"), so the window stays blank. On Linux, when the variable is unset, the Preview plugin sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` as it registers, before WebKit loads. | 2026-10-12, Hyprland 0.56 on Arch, WebKitGTK 2.54.1: a blank preview window, the page drawn with the variable set | WebKitGTK allocates its buffers under XWayland, or WPE WebKit embeds the preview |
| Dispatcher clock (`DispatcherClock`) | [Avalonia #22064](https://github.com/AvaloniaUI/Avalonia/issues/22064): on Wayland the UI dispatcher measures timers on a stopwatch started before the platform's run loop clock, so every timer fires 120 to 260 ms late and animations run at 4 to 7 frames a second. With the Wayland backend, the host points the dispatcher's clock at the platform's by reflection, and does nothing when a later Avalonia no longer has those fields. | 2026-10-10, Hyprland with NVIDIA and AMD, Avalonia 12.1.3: 3 to 9 frames a second, 60 with the clock aligned | Avalonia fixes #22064 |
