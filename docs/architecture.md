## Overview

Avala is a desktop harness for coding agents, written in C# on .NET 10 with Avalonia. It runs each agent in its own git worktree, answers its requests through explicit policies, judges its work by the repository's own checks and accounts for every token it spends.

- **One process, made of plugins.** The host loads every module as a plugin and knows none of them; modules talk through events, contracts and extension points.
- **A pure domain.** Each module's rules are plain, deterministic C#, and its lifecycles are state machines whose [diagrams](diagrams/) are generated from the code.
- **A trust layer.** Verification, Permissions, Supervision and Budgets decide when work is done, what an agent may do, when it is stuck and how much it may spend.
- **A user interface built on contracts.** The Workbench draws every screen from other modules' contracts, view model first.
- **Proven through the simulator.** Every behavior is tested end to end against a simulated harness, and the rules are code that fails with an explanation.

## Modules

### A modular monolith of plugins

Avala ships as one process, but the process knows almost nothing about what it runs. The host is an Avalonia application, a composition root and a plugin loader: it scans its `plugins` folder, instantiates every `IPlugin` it finds and lets each one register its services, handlers and views. The host references no module.

```
src/
  Avala.Sdk               contracts every plugin builds on, no UI framework
  Avala.Sdk.UI            contracts for plugin views, the view registry
  Avala.Runtime           the event bus, the process runner, logs, appearance
  Avala.Shell             the main window's view models and regions
  Avala.Host              the application, composition root and plugin loader
  Shared/                 components, storage and command-line reading every module may use
  Modules/<Module>/
    Avala.<Module>             the module's core: domain, use cases, infrastructure, view models
    Avala.<Module>.UI          optional: its views, and then its plugin entry
    Avala.<Module>.Contracts   optional: public contracts other modules may use
```

- **A module depends only on the SDK, its own projects and other modules' `Contracts`.** Everything else in a module is `internal`; its single public type outside its contracts is its plugin entry, in its `.UI` project when it has one and in its core otherwise.
- **Folders are named after what the code does**, such as `Submission`, `TurnChecks` or `Storage`, never after layers. The layers still exist, Domain, Application, Infrastructure and ViewModels, and a single layer map in the architecture tests assigns every namespace to one, so dependencies keep pointing inward.
- **All plugins share one load context**, so a contract has one type identity for every module: the `IAgentProvider` the simulator implements is the one Agents asks for.

A new capability, such as an issue tracker or another way to isolate work, arrives as a new module, without touching the core. It talks to the rest of Avala in three ways only:

| Mechanism | Use it to |
| --- | --- |
| Integration events on the bus | React to what happened |
| Contracts injected through dependency injection | Ask for an answer or an action |
| Extension points the core defines and plugins implement | Let the core use something it does not know, such as `IAgentProvider`, `ICompletionGate`, `IApprovalStrategy`, `IJobAdmission` or Autopilot's `IJobSource` |

### Agents and the provider contract

`Avala.Agents.Contracts` is the only thing a provider plugin depends on. A provider implements `IAgentProvider`: it starts an `IAgentSession` that streams agnostic events, such as turns, messages, reasoning, file edits, commands, permission requests, forms, usage and limits, and accepts turns, permission decisions, form answers and interruptions. The Agents module checks every event of every turn against one `Turn` aggregate, so a provider translates a protocol and never re-derives lifecycle rules.

Providers do not declare a fixed list of flags. Each capability is a **component**: a small sealed record such as `Interruptible`, `Resumable`, `AcceptsTools`, `AsksForms` or `ReportsLimits` with the windows it reports, attached to a `CapabilitySet` per connection. The core's systems query the components they know and ignore the rest, so behavior depends on declared capabilities, never on a provider's name. A plugin may define components of its own.

Sessions open on **connections**: one harness with one account, credential and configuration, several per harness if you like. Avala offers its own harness tools, such as the canvas, delegation and follow-ups, to every provider that accepts them, and each harness adapts to that offer through its plugin. A conformance kit checks every provider against the contract.

Claude Code is the first real provider: it runs the `claude` CLI in its streaming JSON mode and serves Avala's permission prompt and harness tools from an MCP server inside the session. The CLI hides MCP tools behind its tool search until the model looks for them, so a model asked for a chart never saw the canvas and wrote an HTML page instead; when a session is offered the canvas, the plugin lists it to load up front (`_meta` `anthropic/alwaysLoad`) and appends a short system prompt that asks the model to show anything visual on it, in the formats the canvas offers, instead of writing a page or opening a browser. The canvas runs no CSS keyframes and no script, and nothing on it responds to input, so the canvas tool's description and the prompt send anything that must respond to input, such as an interactive chart, a three.js scene or an app, to a page: when the Preview plugin offers its `PreviewOffer` to a provider that declares `AcceptsPreview`, as Claude Code does, the prompt asks for a page kept in the worktree with its libraries vendored, served on 127.0.0.1 at `$AVALA_PORT` from the ports `$AVALA_PORTS`, and its URL told to the person, since Avala shows it in its [preview](#previews) beside the conversation, and never a browser opened or a screenshot taken; without that offer, it asks for a self-contained HTML file, whose path the person opens from its line.

A Claude Code session can go on working after a `result` when the agent left a sub-agent or a shell command running in the background. Such work is part of its turn: a provider reports it with the agnostic event `ItemBackgrounded`, which keeps the item open and the turn live until its `ItemCompleted`. The `Turn` never expires such an item and closes it as abandoned if the turn ends first; Supervision counts the wait as harness time, like a pending harness call. Claude Code reports it from the `system` message `task_started` and from the async launch's tool result, closes it from `task_notification`, and while any is pending carries a successful `result` instead of ending the turn, so the job stays running, its session is never rested under it and a message joins its turn. An error `result` still ends the turn, and the conversation says which background work it lost. An interrupt is sent to the CLI whenever background work is in flight, so the CLI stops it; when the CLI owes no `result`, because its own turn already ended and only background work kept the turn live, the adapter ends the turn `Interrupted` on the interrupt's acknowledgement, and the work the CLI reports `stopped` ends stopped, not lost. A turn the harness begins without a message from Avala, such as Claude Code waking for a background agent's notification, is marked `TurnStarted.Woken`; `AgentSessions` publishes `TurnWoken`, and when its job awaits review in that session `CheckTurn` withdraws the review with `Job.Wake`, an attempt of origin `Woken`, so the turn is the job's and is judged when it ends. Supervision keeps the state of the live turn, a person's pending answer and the calls it awaits, when its job starts running, and resets it only when the job moves to another session.

When no turn is live and the session calls a tool (`tools/call`), says something (`assistant` or `stream_event`) or receives a task notification, the conversation opens a turn of its own, as it does for a message from a phone, serves the call and shows what is said, and the next `result` closes it. Its end is judged only while the job runs: on a job awaiting review it adds to the conversation and changes nothing else. A message Avala sends while such a turn is live joins it instead of failing the job. Stopping a session closes its live turn, so no turn stays open with nothing running; stopping every session at shutdown publishes nothing, and the restart note names the background work lost with the previous run. The MCP handshake, `initialize` and `tools/list`, never opens a turn, nor does anything that arrives after an interrupt until the results it still owes have come.

The tools that act on the agent's own background work, `TaskOutput`, `BashOutput`, `TaskStop`, `KillShell` and `SendMessage`, are allowed when the CLI asks, and a successful stop ends the item it stopped. A session declares the folders its harness keeps for it, `OwnFolders` on `SessionOpened`; Claude Code declares its project folder of transcripts, tool results and task output, so the agent reads its own records without a person. An `Agent` call that would run in an isolated worktree of the main repository is decided by the policy before it launches, rather than having its writes denied one by one.

### The trust layer

Avala's purpose is agents you can trust without watching. Four modules carry that, each a plugin built on the extension points above.

**Verification.** A job is done only when the checks its repository declares pass in its worktree. Verification registers a completion gate that runs those checks after every finished turn and keeps the evidence of every attempt; the review shows that verdict first.

**Permissions.** Every permission request and every question an agent asks goes through an explicit policy, built-in guards and defaults around the rules the repository commits, at the level of autonomy the job allows. Sessions always open asking before every edit and command, so nothing bypasses the policy. Every decision is audited with the reason it was made, including the ones left to a person.

- A line whose every part only reads inside the worktree, such as `ls`, `grep`, `git status` or `git log` without a redirection to a file, runs without asking, audited as "read-only allowed", unless a repository rule says otherwise.
- A read outside the worktree, such as another repository the job learns from, is allowed without asking, even under autonomous, when its real path, links followed, is inside a readable folder: the folders `readable.json` in the data folder names, or the projects folder until that file exists, read through `IReadableFolders`. A harness says which path a request reads as `PermissionRequested.Reads`; Claude Code sends it for `Read`, `Grep`, `Glob`, `LS` and `NotebookRead`. The session's own folders and the job's scratch folder are readable the same way, for reads only. The built-in rule "reads-in-readable-folders" comes after the repository's rules, so a repository can still deny it, and never matches an edit, which still goes to a person. A read-only command line counts a path in a readable folder as inside.
- Every process of a job gets `TMPDIR`, `TEMP` and `TMP` pointing at a scratch folder of its worktree under the data folder's `temp` folder, created when the worktree's first process tree opens and removed when the job ends. The policy counts a write resolved inside it as inside the workspace, so temporary files never wait for a person or get denied under autonomous, and they never show in the job's diff.
- A person answers a request once, always for its program in this job (one rule per program a chained line still needs, with any arguments; for the web its host, for a tool its name), or with everything in this job, which runs the rest of the job at autonomous with the guards still first. A repository that declares itself supervised keeps that ceiling, and one without a declared level lets a person raise its job.
- Under autonomous, a request the policy denies leaves a card in the conversation, Denied with what was asked, that never holds the turn. When a job rule could allow it, Allow and retry keeps that rule for the job through `IDeniedRequests`, records it as a person's answer and tells the agent, the way the composer sends a message, that it may retry; a denial a guard keeps for a person says so and offers nothing.
- A job that needs a folder outside its worktree, such as another repository to update, asks once with the executed harness tool `request_folder`, its folder, `read` or `edit`, and why. A session can call it before Jobs has told Permissions which job it runs, so `FolderDesk` first waits, up to 30 seconds, for `GovernanceBook.WorkingAsync` to see the session's job. It then answers at once a malformed call, a session still without a job, a folder inside the worktree, a missing one and one the job may already reach; any other call becomes a `PolicyDecision` of kind `Other` whose `Folder` holds the request, left to a person even under autonomous, and the tool's result waits for the answer. The person grants read only (`Remember.ReadsInThisFolder`) or read and edit (`Remember.EditsInThisFolder`) through `HumanAnswers`, which keeps a job rule of scope `Granted`, origin `Job`, for the folder's real path, and returns the result to the agent. `RequestPlaces` counts every granted folder as readable, and an edit-granted folder fills `PermissionRequest.Granted` for an edit whose real path lies in it, unless the path is under a `.git` or is a `.avala/permissions.json`, so those guards still ask; only a `Granted` rule matches it, and the guard for edits outside the worktree no longer applies. A command that runs in a granted folder is still decided on its own. An edit outside the worktree with no grant carries its repository, found by `IRealPaths.Repository`, as `JobScope.Folder` when that grant would allow it, so its card offers "Always in *repository* for this job" and its autonomous Denied card can allow and retry it the same way. A repository file cannot declare the `Granted` scope, and its rules die with the job like any other job rule.

**Supervision.** An agent that goes silent is noticed and its job held, with the facts that were measured, instead of hanging forever. A session that dies is caught by Jobs and held as lost. A job whose start throws, or whose worktree git cannot prepare, is held as could not start with the error's message instead of staying in Preparing: the exception is logged at error level, the hold survives a restart, the sidebar says "could not start", and the inspector's worktree section shows the message, its home folder masked, with Retry, which removes the worktree the failed start left, only one Workspaces made for the job, and launches the job again from its repository. Such a job takes no message until it has started.

**Budgets.** Caps on cost, tokens, memory and provider limits stop a job before it overspends; a child job's budget is carved out of its parent's, and the machine admits only as many running jobs as its limit allows. Every intervention is recorded.

Around them, **Resources** samples the processes, ports and disk every job uses, reaps what a session leaves behind, leases ports per worktree and reclaims old worktrees, and **Observability** keeps usage, cost and limits per provider, account, connection, session and job. A port lease skips the blocks in which a port is listened on, and holds every port of its block through a claim file in the machine's temporary folder, `avala-ports/<port>.claim`, opened without sharing until the lease is released or Avala exits, so two Avala processes, or test runs in parallel, never lease the same block before its service binds it.

### Unattended work

**Autopilot** runs a backlog unattended and approves a job automatically only on clean evidence. **Delegation** lets an orchestrating agent hand work to child jobs that are governed and verified like any other. Its tools are offered only in a worktree whose committed `.avala/jobs.json` declares a `delegation` section: a module may register an `IHarnessToolGate`, which Agents asks for every harness tool when a session opens, so an agent knows from its first turn what it cannot use. A child's report gives its orchestrator its state, its kind (`crossHarness`), its harness and, when it failed, why. `delegate` may name one of the section's connections, and `stop_child` discards one of the caller's children; `subagents`, offered to every agent that takes executed tools, lists the job's sub-agents, in-process and delegated, with their states, folded from its live activity and the transcripts of its earlier runs. A child held at its usage limit is not settled: its parent's call returns early with the hold, and Handoffs, asking each `IHandoffTerms`, hands it among the section's connections where no limits are declared.

A job that fails keeps its reason, `JobFailure`: its worktree could not be prepared, no connection could run it, its connection does not offer its model, its agent's turn failed or its agent could not take a message. It is stored with the job, published with `JobProgressed` and shown in its composer.

**Triggers** starts work unattended, on a schedule, on a signed webhook received on a loopback port only, or on a forge event such as an issue labeled, a command in a comment, failing checks on a branch or a review requested, as ordinary jobs that never exceed their repository's autonomy. Forge events are polled through the forge plugins, so a laptop needs no public endpoint: the first poll only records where the forge stands, each event is judged against the trigger's filter and an explicit list of authors checked against who acted, fires at most once and moves the stored cursor only once its fire is recorded, and a forge's own signed webhook only asks for a poll at once. A forge trigger's instruction is filled from its event, so it is never run by hand: Check now on the Triggers page polls it at once instead. Avala never opens a public port: receiving webhooks from the internet takes a tunnel of your own, such as Tailscale Funnel.

### Repositories and accounts

**Repositories** come from a person, never from an agent. Workspaces owns git: it makes a folder a repository, creates a new one, clones an address into a new folder under a chosen parent and publishes a repository to a remote, always through the process runner, with terminal prompts turned off, so a refused credential is reported as unauthorized instead of waiting on a prompt nobody sees. A failed or cancelled clone removes only the folder Avala made for it, and never follows a link inside it.

Forges creates the repository on a forge connection of `forges.json`, for the account of its token, through an optional capability a forge plugin implements (`IForgeRepositories`): GitHub, Gitea and Forgejo through their APIs, and the simulated forge as a bare remote under the data folder. Avala then adds it as `origin`, over HTTPS when git has a credential helper for that host and over SSH otherwise, and pushes the current branch with its upstream, using the person's own git credentials; Avala never holds a token for git. Publishing again when `origin` already is that repository only pushes, so a push refused for credentials can be retried once they are fixed. Publishing and cloning are commands of the interface only: no agent is offered them as a tool.

**Accounts** are the harness connections and the forge connections of `forges.json`, shown together first in Settings, above the repository rules. Forges writes `forges.json` through `IForgeConnections`, one write at a time through a file moved into place, keeping its poll interval and every other entry. It also finds the accounts this computer already signs in with: a forge plugin may declare `IForgeLogins`, the command that lists its command-line logins and how to read them, such as `gh auth status` or `tea login list`, and the names of its token variables. The core runs those commands through the process runner and only checks whether a token variable is set: it records names and references, never a value, so a found account is added with one click and nothing is written without the person. A login one tool holds for two forges, such as tea for Gitea and Forgejo, is told apart by probing the host. `ISourceControlAccounts` names who each account signs in as through the optional `IForgeAccounts`, and lists an account's repositories, most recently changed first, through `IForgeRepositories`, with the address to clone them chosen as publishing chooses it. Harness logins are discovered again on request, so one made while Avala runs appears without a restart.

Workspaces keeps the projects folder clones go into, the first of `~/Projects`, `~/projects`, `~/code`, `~/src`, `~/dev` and `~/source/repos` that exists until a person chooses one, asked for once and kept in `workspaces.json`.

### Jobs without a repository

Every job runs against a git repository, so a job started without one gets a repository of its own. The welcome's composer, No repository in New job's repository pop-up, which is its choice when no job ran yet or the last job ran without one, or Ctrl/⌘+Shift+Enter in its instruction, asks Workspaces' `IScratchRepositories` for a scratch repository and submits the job there as any other: its own worktree, the permissions of a repository that declares none, the budgets, verification and review.

A scratch repository lives in the data folder's `scratch` folder, named after the local day, the first four plain words of the instruction and a short random id, such as `scratch/2026-10-12-sketch-a-csv-parser-3f9a1c`, with a fresh id when a name is taken. Its first commit holds only `.avala/jobs.json` declaring `merge`, so approving a job lands its work on the scratch repository's branch where Open folder finds it; it declares no checks, so verification says so and the review still shows the diff. When git knows no identity, that first commit is made under Avala's name, as Avala's own checkpoints and merges are, so a scratch job works out of the box; making or initializing a repository of your own still refuses without one. Scratch repositories are never suggested as a job's repository, their jobs are listed under Chats in the sidebar, and the inspector's worktree section names the folder and opens it. They hold work, so Avala keeps them and never deletes anything there; keeping one as a regular repository means moving it out of `scratch` yourself.

### Continuing a job from a phone

A provider that can hand its session to a phone declares `ControlsRemotely`, with `StartsOn` when its own setting says every job should start that way. Only a job its person started, the root of a delegation tree or a chat without a repository, can be remote-controlled: the Job aggregate refuses a delegated job (`NotRoot`), so the phone shows one session per piece of work and follows the children through it. Jobs keeps the person's choice on the job and asks the session through `IAgents.ControlRemotelyAsync` whenever the job is recorded: on while it runs, checks or awaits review, off while it is held, so a device never gets past a budget or a limit. The session reports its state and link as `RemoteControlChanged`, which the Agents module publishes as `RemoteControlReported`, outside any turn.

A message sent from the device reaches the core as `RemoteMessageArrived`. During a turn it joins the turn, like a message sent mid-turn from Avala, and the conversation marks it as sent from the phone. When it starts a turn of its own on a job awaiting review, the turn checker, the same handler that judges the end of that turn so the two stay in order, continues the job with an attempt whose origin is `Device`, as a message from Avala would. Its permission requests go through Avala's policy like any other.

Claude Code does it through its Remote Control: the control request `remote_control` turns the bridge on or off in the headless session Avala already runs, `system` `bridge_state` messages report it, and `--replay-user-messages` echoes the device's messages, which carry `origin: human` where Avala's own carry none. Its switch "Start jobs on your phone" is one for every login, kept in `claude-code.json` in the data folder. The header's phone glyph opens a popover with the link and its QR code, drawn by the shared `QrCode` control from QRCoder's modules.

### Attachments and mentions

A message can carry files. `Attachment` in Agents.Contracts names a file, its media type and the path of Avala's own copy: `IJobAttachments` copies what the person picks, drops or pastes into the data folder's `attachments` folder, 20 MB at most, so the agent still gets it when the original moves. A provider declares the media types it takes with `AcceptsAttachments`, where `text/*` takes every text type, and the composer offers attachments only on such a connection and refuses any other type with the reason. The core refuses one too, with `UnacceptedAttachment`, since `IAgents.SayAsync` checks the types before a turn starts or a message joins a turn. Jobs keeps the attachments on the attempt they began, and the conversation shows them as chips under the prompt. Claude Code sends an image as an `image` block, a PDF as a `document` block and a text file as a `text` block wrapped in `<attachment name="…">`, all in the user message's content.

A mention is text. Typing `@` in the composer asks `MentionSource` for suggestions: the files and folders of the job's worktree and its latest commits through `IRepositoryIndex`, a port of Workspaces that runs `git ls-files` and `git log`, and the person's other jobs from the board. The list is kept for 30 seconds per folder. A chosen mention writes `@token` into the draft, and on send the message gains a `Referenced:` list that says what each mention still in the text refers to, so every harness understands it without a capability of its own.

### Best of N

**Contests** runs one request as several candidate jobs and keeps the best by its evidence, never by an agent's word. Each candidate is an ordinary job, in its own worktree with its own session, retries and checks, on the connection a job would take now or spread across the usable connections when asked, and its budget is an even share of the per-job caps, carved by Budgets. Once every candidate has settled, the verdict requires a passing verification, disqualifies a run that edited a rule file or rewrote its checks, and ranks the rest by fewest evidence exceptions, fewest attempts, smallest diff, lowest cost and earliest finish; when nobody passed, the contest waits for you with every candidate shown. Approving any candidate picks it and discards the others, whose worktrees are reclaimed as usual.

Jobs knows nothing of contests: Contests submits and discards jobs through their contracts, keeps its contests in `contests.db`, and recovers them at startup from the job catalog. The `bestOf` section of `.avala/jobs.json` sets how many candidates a job starts with and the most a contest may have, and an answer given "in this contest" to a candidate's permission request goes to every candidate.

### Notifications

**Notifications** tells your phone when a job needs you while you are away from the Avala window: a decision left to you, a held job, a budget or limit hold, a failed job or an ended loop, and a job ready for review if you ask for it. It only listens to other modules' events; only the Workbench reads its contracts, to show its settings.

A notice waits thirty seconds so several become one message, is never sent if you answer in the app first, and is sent only once nobody has touched the Avala window for two minutes, a signal the host offers every plugin through the SDK's `IPresence`. It goes to [ntfy](https://ntfy.sh), on a private random topic by default or a server of your own, with an emoji tag per kind that ntfy shows as an icon, or to a webhook of your own, signed like a trigger webhook. What is sent is minimal by default, the event, the repository, the job's title and a count, and the tool and target are added only if you choose detail, through the same redaction as the log. One notice per job and kind until it is resolved, even across a restart, at most twenty an hour, urgent ones through your quiet hours and the rest in one digest after, retried three times before it is reported failed. `notifications.json` in the data folder holds the settings and names the environment variables of any token or secret, never the secret itself; Settings shows exactly what is sent and sends a test.

### Usage statistics

A packaged release counts installs and daily active installs through [Aptabase](https://aptabase.com), and nothing else. `UsageTelemetry` in the runtime, beside the update check and behind the SDK's `ITelemetry`, sends `installed` once ever and `active` at most once per local day, each with the version, the operating system and its architecture under a random install ID kept in `telemetry.json`. It runs in the background at startup and at local midnight, never blocks the window and retries what failed at the next start.

Only a build packaged with the `AvalaTelemetryKey` property can send, and `DO_NOT_TRACK=1`, `AVALA_TELEMETRY=0` or the person's choice turn it off. The welcome tour's privacy step says what is sent on a first run, with a switch to turn it off, and a section in Settings, About shows the status, the install ID and exactly what is sent. A data folder that already finished the tour without having seen the telemetry notice gets the one-time notice in the sidebar's footer instead; a finished or skipped tour counts the notice as shown. [Releasing](release.md#usage-statistics) has the details.

## Cross-cutting rules

### The domain

Each module's domain is plain, deterministic C#: no I/O, no async methods, no exceptions. Aggregates are sealed classes with factory methods and no public setters; every public operation returns a `Result<TEvent, TError>`, absence is an `Option<T>` rather than `null`, and each module that can reject an operation has one error enum. Lifecycles such as a job's are state machines built on Stateless, fired only through the guarded transition helper, and their [diagrams](diagrams/) are generated from the code.

### The event bus

Modules learn what happened through integration events on an in-process bus, implemented in `Avala.Runtime` over `System.Threading.Channels`. Publishing never blocks: one router reads events in publishing order and posts each to the mailbox of every handler of its type. Each handler has its own mailbox and reader loop, so it sees its events one at a time, in order, and keeps plain state without locks; a slow or failing handler delays or fails only itself. Events state facts: nothing asks a question over the bus and waits for a reply, since a contract makes that dependency explicit.

The same discipline holds everywhere: concurrency between components goes through the bus or channels only, and nothing waits on time where it could await the event that states the thing happened.

### Shared rule files

Several modules read their own section of one file, such as `.avala/jobs.json`. Each reads the file through `JsonSections` in the SDK: the whole file must be one JSON object without duplicate fields, any other module's section may nest as deep as it needs, and only the module's own section is bounded to its depth and checked strictly. Jobs owns the file's overall shape and rejects a field or a nesting the format does not define. A section one module cannot read therefore never makes another module reject the file.

### Startup and shutdown

The runtime starts on the thread pool, whoever starts it: the router and the startup tasks never run on the UI thread, so only handlers that change what the interface shows marshal to it, through `IUiDispatcher`. Startup runs in stages. In `Open`, every module opens and migrates its own database, all at once since no two share a file; then the `Restore` tasks run one after another, then `Recovery`, and `StartupCompleted` follows.

Nothing Avala starts outlives it. Stopping the application disposes the process runner, which cancels every process it still runs, kills its tree and returns only once each has exited, and refuses to start another; a read nobody awaits, such as the inspector checking a repository's remote, therefore never keeps a repository's folder in use after Avala stops.

## Persistence

Each module owns its data in its own SQLite database under the data folder, through EF Core with migrations, and no module reads another module's data. Every fact a screen presents as part of a job's record, such as the job, its usage, its evidence, its audit and its conversation, survives a restart; what belongs to a live session, such as a pending permission, dies with it. Database work never runs on the UI thread, and an architecture test checks that every module's model matches its latest migration.

Settings that are not a module's records live as small JSON files in the data folder, such as `appearance.json`, `layout.json`, `onboarding.json`, `workspaces.json`, `forges.json`, `notifications.json`, `telemetry.json` and `updates.json`. Rules a repository commits live in its own `.avala` folder, which an agent cannot edit.

## The Workbench

### Regions and view models

The Workbench is the module of the user interface, built on other modules' contracts only. It follows MVVM, view model first: view models live in the module's core assembly and reference no UI framework, and views live in its `.UI` assembly, so another UI technology means replacing the `.UI` assemblies and nothing else. A view only binds, with compiled bindings, theme resources and commands, binds a selection through `Kept.Selection` so a view torn down cannot clear it, and takes every shortcut and the label its tooltip shows from `Hotkeys`, which presses ⌘ on macOS and Ctrl elsewhere; a text cut by its trimming offers itself whole as a tooltip through `TrimmedTip`, and a text shown whole offers none; the view registry picks the view for each view model.

The main window is drawn as named **regions**, an idea taken from Prism: a page declares its regions, plugins register view models into them, and a region's context, such as the selected job, reaches every component in it, so a page never knows the components other modules contribute. Settings works the same way: `WorkbenchRegions.Settings` holds the sections a harness contributes, drawn in the machine's part of Settings and activated with it, such as Claude Code's compaction settings, so the Workbench never names a harness. Components that live apart talk through small UI messages over an injected messenger. Every view model has a design-time implementation, so every view renders in the designer, and every component has scripted acceptance tests that drive it as a user would, headless.

### The welcome and the harness chip

The jobs page shows a welcome whenever no job is selected: one composer that starts a scratch job, with a chip inside it that names the connection Auto would pick now and why, and opens a menu of Auto and each usable connection with its usage, then the model and effort of a chosen connection, a choice kept for the next chat until Avala restarts; cards that open a folder, clone or make a repository; and a chip per account whose status dot turns amber with its one fix. The whole welcome shows whenever no job is selected, whether or not jobs exist: it is only on screen when no conversation is, and a conversation brings its own composer, so a compact variant would only hide the ways to start.

The conversation's composer shows the same chip, one view model and view (`HarnessChoiceViewModel`) fed by the welcome's `WelcomeHarness` and by each conversation's `JobHarness`: it reads the job's connection, model and effort, the chosen ones or else the ones its harness reported, and its menu lists the job's connection, then "Continue on" each other usable connection, then the model and effort. A job that is held or awaits review, on a harness that resumes conversations and offers models, takes another model or effort through `IJobs.ChooseModelAsync`: Jobs stores it with the job, stops the idle session, and the next message resumes the conversation in a new session with it. A held job continues on another connection through Handoffs' `IHandoffRequests`, the same handoff and brief as at a usage limit, recorded as the person's choice. While the agent works, both stay visible and read only.

### The welcome tour

A first run opens the **welcome tour**, a centered sheet drawn over the whole window through the shell's `Overlay` region, in four steps a person moves through with Continue or Enter, shown by step dots, and leaves at any step with Skip or Esc:

1. Welcome, with the logo and what Avala is in one line.
2. Your agents, a row per connection with its harness and a mark for signed in, at its limit or signed out, the last found by checking the connection's credential, or, with none, the install command each harness declares through `ProviderInfo.Install` and `ProviderInfo.SignIn`, copied in one click, and Check again.
3. Your code, the projects folder with Change… and the source control accounts found on the computer, each added in one click.
4. Your privacy, the switches for hiding personal details and for usage statistics, bound to the same settings as Settings, ending with Start on the full welcome.

Each step slides in from the right, and appears in place under reduced motion. Finishing or skipping writes `onboarding.json` next to `appearance.json` through the SDK's `IOnboarding`, so a fresh data folder shows the tour and every later start does not; Settings, About reopens it with Show welcome tour, through a `TourRequested` message.

### The sidebar

The sidebar groups jobs by project from one board: the Workbench's `ProjectKeeper` keeps the Projects module's `ProjectMap` on the `JobBoard` from `ProjectsRestored`, `ProjectCreated`, `ProjectRenamed`, `ProjectDeleted` and `ConversationMoved`, as `ContestKeeper` keeps contests, so a change of projects regroups the rows without another read. Needs you stays above every project, so a job waiting for a person never hides inside a folded project. Every other row goes into its project, `ProjectMap.Of`: where a person moved the job, otherwise its repository's project; a job in a scratch repository goes into Chats, and a job whose repository's project has not arrived yet sits under a group named after its folder until it does. Delegated children stay under their parent and a contest under one row, as before. A project's done jobs fold under "N done", and folded groups are interface state, kept in `layout.json` as `collapsedGroups` through `IWindowLayout`, never in the Projects module.

Renaming, deleting and moving go through the Workbench's `ProjectShelf` to `IProjects`, and the sidebar shows the result when the event comes back; a refused name or deletion is said in the group, in words the Workbench chooses from `ProjectRejection`. The Projects module makes a repository's project the first time that repository runs a job, at startup for jobs of earlier runs that were never moved and are not archived, and when an archived job that was never moved is restored, so a repository's project deleted once empty stays gone until the repository runs again or one of its archived conversations comes back. Archived conversations do not keep a repository's project from being deleted.

Archiving is a shelf, not a state: the Projects module keeps the archived job ids in `projects.db` and on `ProjectMap.Archived`, publishes `ConversationsArchived` and `ConversationRestored`, and never touches the job. Its domain allows a root job that is held, ready for review, approved, discarded or failed, and refuses one that works (`StillWorking`) or is a sub-agent (`FollowsItsParent`); `ArchiveReturns` restores an archived job whose `JobProgressed` says it is preparing, running or checking, never one only held again, so a held job a person archived does not come back by itself, and the startup pass does the same for jobs that worked while Avala was closed, so archiving never hides work. The sidebar places no row whose jobs are archived, which keeps it small, and moves the selection to the next row of the group when the selected one leaves. Overview leaves them out too: `ArchivedJobs` hides a job that is archived, shares a contest with an archived candidate or descends from one, and `FleetReader` and `DelegationReader.OrchestratorsAsync` skip what it hides, so Connections and Delegation list no archived conversation. Connections then shows only the jobs in progress, those that work, wait or need you, until **Ready for review** or **All** is chosen; each choice counts its jobs (`FleetScope`). The Workbench's `ArchivedReader` reads the archived conversations from the board, one per root job or contest, for the Archived page, the Archived row in the sidebar footer and the Archived chip in the job's header.

### The conversation

The conversation copies through `IClipboard`, a port of the SDK that the shared components implement with the platform's clipboard, so a view model copies a reply or a prompt without knowing the UI framework, and tests use a fake. Presentation that is only about time stays in the views: the checkmark a copy shows for a moment and the elapsed time of the working row and of a running job's sidebar row tick on the dispatcher, from a start time the view model hands down, and the views read their clock from an inherited `ElapsedText.Clock`, so a test sets a fake clock instead of waiting. The send key is part of the appearance kept in `appearance.json`: Enter sends and Shift+Enter adds a line, or Command (Control elsewhere) with Enter sends when chosen in Settings; the composer reads the choice at the moment a key is pressed, so a change applies to every open conversation at once.

A code block in a reply is colored by the TextMate grammar its fence names, through `MarkView.Avalonia.SyntaxHighlighting`'s TextMateSharp grammars, in the colors of Visual Studio Code: each token's scopes are matched against VS Code's Dark+ and Light+ themes, and the token keeps both colors, so the block follows the app's light or dark theme the way the editor a developer uses all day does. A block shows its code as plain text at once; once it is on screen, `CodeColors` tokenizes it on a `SerialExecutor` in chunks of 60 lines, keeps the result by language and code (8 MB at most, and never a block that would take half of it), and the block is painted at background priority in one pass, so a block seen before is colored as soon as it is shown. `CodeText` draws the colors as style overrides of a single text layout rather than one `Run` per token, because Avalonia lays inlines out in time quadratic in their number: a 120-line block went from 545 ms to 95 ms on the UI thread. Every block is colored whatever its length: a painted layout costs at most about twice the plain one (10,000 lines: 0.9 s against 0.6 s to lay out, headless), and the plain layout of such a block is already the larger cost. A block of 30 lines or more numbers its lines in a gutter drawn from the code's own text lines, so a wrapped line keeps one number.

A code block's header says its language and length, and on hover offers icons to wrap lines, save the code and open it in an editor. The block asks its `MarkdownText` to carry the request out through a `CodeCommand`, so the shared component knows no service: the reply's view model saves through `IFileSaver` and opens through `IFileOpener`, after writing the code to Avala's own `code` folder under a name made from its hash and its language's extension. Dragging across a block's code selects it and copies the selection to the clipboard when the button is released. `MarkView` selects across a whole reply by taking the pointer once a drag moves three pixels, and it only knows a code block that is a bare text block, so `CodeText` takes the pointer back for a drag that began in it; its transparent background makes the whole block, not only its glyphs, answer the pointer.

Replies are drawn with GitHub callouts (`> [!NOTE]` and the other four kinds), footnotes and math. Math is typeset with CSharpMath, which draws on the SkiaSharp canvas Avalonia already uses; MarkView's own math package needs SkiaSharp 4, which Avalonia 12 does not load. A formula that does not parse is shown as its source. A table wider than the reading width scrolls sideways inside the reply while the wheel still scrolls the conversation.

A reply links the files, commits and issues it mentions. `References` finds them as the Markdown is parsed: a path with a folder or a source file's extension, with an optional `:line`, in text or inline code; a hash of 7 to 40 hexadecimal characters with both letters and digits; and `#` followed by a number. They become `avala-ref:` links, which only the reply's view model understands: a file opens in a peek, a sheet like Quick Look that shows the file from the job's worktree scrolled to the line and marking it, and a commit or an issue opens on the web page of the repository's `origin` remote. Code blocks and links the agent wrote are left as they are.

When a conversation has been idle longer than its harness keeps the prompt cache, and its context holds 100,000 tokens or more, the composer says what the next message will re-read and offers to compact it first. The core knows only two capabilities a provider declares: `CachesPrompt(Lifetime)` and `CompactsOnRequest(Message)`; what the lifetime is and which message compacts belong to the provider.

The job's more menu copies the conversation as Markdown or exports it to a file: `TranscriptMarkdown` writes it in the Workbench's application layer from the same `Transcript` the conversation shows, prompts and replies as they are, each tool as one line with its output in a fenced block only when it is expanded on screen, and reasoning left out; the file is chosen and written through `IFileSaver`, a port of the SDK the shared components implement with the platform's save dialog.

A file edit's line expands into the diff of that edit alone, read from the edit's input, which every harness gives as removed lines marked `- ` and added lines marked `+ `, or as the whole content of a written file; long edits show their first 400 lines. An edit and a hunk are drawn by `CodeDiff`, one text line per diff line, colored through `CodeColors` in the language their path's extension names, or its file name when it has none, such as `Dockerfile`. The code before the change, its context and removed lines, and the code after it, its context and added lines, are tokenized each on its own, so a comment opened on a removed line never colors the lines that follow it in the new code; the marks and the notes that are not code stay plain. A diff line is a `TextBlock` of a few runs rather than a `CodeText`, because a diff is short and each line needs its own background. A command's input is a `CodeSnippet`, a `CodeText` colored as `shellscript`, and its output stays plain text. From the expanded edit, an icon opens every change to the file against the job's base in a popover, through `WorkedFiles`, which reads the diff of the job's workspace and is drawn with the review's `HunkView`; the file is the path its title names after `Write ` or `Edit `, the shape every harness gives a file edit's title, and a title cut short names no file. A written image, SVG or HTML file offers a preview on its line: `WorkedFiles` finds the file in the job's worktree, or in its repository once the worktree is gone, through `IWorkingFiles`, which never reads outside the folder it is given. An image is decoded off the UI thread through `IPictureDecoder` at the width it is shown at, never wider than the image itself: 520 pixels for the thumbnail, the sheet's width times the screen's scale once the sheet opens. The preview's view model holds the decoded picture only while its row is realized (`Realized`) or its sheet is open, so the thumbnail and the sheet share one picture, and releases it when the row scrolls away or the job is left. `PictureCache` keeps released pictures by content and width until they exceed 64 MB, then disposes the oldest. An SVG is handed to the canvas renderers as a `CanvasRendering`, so it is sanitized and drawn exactly like an SVG canvas, and a small one also shows as a thumbnail under its line; a page is opened in the person's browser through `ILinkOpener`, since Avala draws no HTML.

### Canvases

The canvas plays SVG animations written in SMIL (`<animate>`, `<animateTransform>`, `<animateMotion>`, `<set>`), which Svg.Skia evaluates; it runs no CSS keyframes and no script, and nothing on it responds to input.

An SVG takes the size of its `viewBox`, which the sanitizer writes as its width and height, and is laid out at that size inside a uniform fit that scales it up or down to the canvas's width, up to the card's height, so a still and an animated drawing of the same `viewBox` take the same space and the card's height follows the drawing; the animating control composes its layers at the drawing's own size. Each SVG is parsed off the UI thread, once per content, and kept among the most recently drawn up to 64 MB of parsed pictures, an evicted one disposed as soon as no view on screen holds it; its card shows an empty area of the drawing's size until it is drawn, while a new version of a canvas keeps the previous drawing on screen until the new one is drawn (`CanvasPresenter.IsDrawing` and its `Drawn` event).

A still drawing stays a plain image; an animated one is drawn by Svg.Skia's animating control, which composes only the layers that move, and it plays only while it is on screen: it pauses when the drawing is detached, scrolled out of view, hidden or its window minimized, and stops when a finite animation has ended. It never takes the pointer or the wheel, so scrolling over it scrolls the conversation. With reduced motion it shows where its animations settle instead of their first frame, and a play button on hover plays it once.

**Open** shows the canvas in a focused card. A diagram, SVG or Mermaid, is drawn there inside the same `ZoomSurface` and zoom bar as the Docs pane's C4 player, at its own size and fitted to the card each time it opens; the surface gets `Zoomed` and the scrolling presenter `Scrolled`, so the drawing is built once. Markdown and source keep a `ScrollViewer`, because text laid out at an unbounded width would not wrap.

### The delegation pane

A job that delegated, or one of its children, offers the **Delegation** pane from its header. The pane is a second `IPane` of the preview region, so it shares the preview's column, width and focus mode; `JobRegions` keeps one pane open at a time, and opening one closes the other through `IPane.Close`. It shows the tree of the job's root through `DelegationReader` and `SubagentTreeViewModel`, the same component Overview › Delegation draws, and marks the job being viewed. `AgentBranches` turns a `DelegationTree` into one tree of `AgentBranch`es: the orchestrator at the root, and under every job its harness's own sub-agents, the tool rows of kind `Subagent` every provider reports, beside its delegated children, each child marked cross-harness when its session's provider is not its parent's, nested to any depth and ordered waiting, failed or lost, working, then settled. `SubagentTreeViewModel` flattens it in pre-order into one card per branch, `OrchestratorCardViewModel`, `DelegationNodeViewModel` or `SubagentViewModel`, each composed with a `BranchPlaceViewModel` that holds its depth, kind, state, edge and fold; a card folded by the person hides its whole branch, more than three settled branches under one card fold into a `FoldedBranchesViewModel` count that opens onto them, and cards are kept by key so a refresh, a fold or a branch that settles never rebuilds one. A branch whose agent ended leaves the tree `SubagentTreeViewModel.Linger` after its orchestrator stops needing it: a completed or stopped one at once, a failed or lost one when it is a harness's own sub-agent or background command, a child with a report, one the person told its orchestrator about, or one whose orchestrator has ended. Only the job being viewed stays. Its header counts the agents, how many work, how many need you, with a flyout of `WaitingAgentViewModel`s that open their job, and the tree's spend. The view lays the cards out with `AgentTreePanel`: the orchestrator on top, its first level side by side under a comb, deeper levels on a rail under their parent, and rails for every level when the comb does not fit, as in the pane; a tree narrower than its room stands centred in it (`AgentTreeLayout.Centered`), and rails keep to the left; each line takes its card's `EdgeKind`, flowing, attention, quiet or failure. A provider without sub-agents shows none. A provider that knows which sub-agent ran a tool says so in `ItemStarted.Parent`, and reports the sub-agent's tokens with `ItemTokensReported`; the transcript then adds no row for the tool but counts it on the sub-agent's row with its title and tokens, which its card shows, so the conversation keeps one row per sub-agent. Claude Code takes both from `parent_tool_use_id` and the usage of the sub-agent's messages. A child's card opens onto its details, one at a time (`TreeOrder.OneOpen`); `AgentGlance` reads a job's context left from its last `ContextReported`, its tokens from its usage and its last three tool rows, which the transcript now stamps with the time they started. Overview, Delegation reads every tree `DelegationReader.OrchestratorsAsync` lists into an `OrchestrationViewModel` each, kept by its root across refreshes, and `DelegationViewModel` filters them by state, repository and connection and orders them by their latest activity. Peek reuses the job's own `ConversationViewModel` from `Conversations`, the one the main view shows, so the rows, cards and composer behave the same in both places; `PeekViewModel` keeps its last rows, and `RowActions` follows a peeked row on every refresh. A sub-agent's card lists its `Trail`, the titles of the tools it ran, which the transcript keeps under its row. Every sub-agent, the harness's own or a delegated child on any harness, shows one state from `SubagentState` in `Delegation.Contracts`: working, waiting, completed, failed, stopped or lost. A harness's own sub-agent waits only while a permission or a question one of its own tools asked waits for a person, and its job does not wait for it, is stopped when its row was cancelled and lost when its turn, its session or Avala ended while it still worked in the background; a delegated child's state comes from its job, lost when it was held because its session was lost. A child's card names its harness and connection. The pane opens by itself when the viewed job starts a sub-agent: it notes the sub-agents already running when a job is shown, and any later one opens it unless it is open already. The header's glyph and the pane talk through UI messages, `DelegationPaneRequested` and `DelegationPaneChanged`.

### Previews

A job's page or app shows in a **preview** beside its conversation, from the Preview plugin. It watches every sample of Resources: a process of a job's tree listening on a port offers that job's preview, as `PreviewAvailable`, labelled unleased when the port is outside the job's lease, and the preview is withdrawn, as `PreviewGone`, when the server stops or the job ends. Run, in the job's header, starts the worktree's `dev` script, or `start`, with the package manager its lock file names, in a process tree of the worktree whose lease reaches it as `AVALA_PORT`, `PORT` and `HOST=127.0.0.1`, and stops with the job; a worktree with no script but an `index.html` has it served instead.

No page loads straight from the agent's server: every preview goes through a loopback gateway on a lease of the job's own, a proxy that bridges the server's WebSockets for hot reload, or a static server confined to the worktree, and both add a Content-Security-Policy that keeps other origins out, so a page fetches nothing from the internet until Allow network is on, for that job until Avala restarts. A top-level navigation is checked against an allow-list in the domain, the loopback ports of the job's lease, its listeners and its gateways, and files that resolve inside its worktree, links followed; anything else, a new window included, is cancelled and offered to the browser with one click.

The page is drawn by the operating system's web view through `Avalonia.Controls.WebView` behind an `IWebSurface` port of the Preview contracts, with private storage and no developer tools: embedded where the platform embeds it (WebView2, WKWebView, WPE WebKit), in a window of its own where it only offers one (WebKitGTK under native Wayland, which only embeds through X11), and otherwise the pane says so and offers the browser. On Linux, WPE WebKit embeds only when it is built with its libwpe backend, `libWPEWebKit-2.0.so.1` with `libwpe-1.0.so.1` and `libWPEBackend-fdo-1.0.so.1`, which `Avalonia.Controls.WebView` 12.1 binds through `webkit_web_view_backend_new`; a WPE WebKit that ships only the newer WPE Platform API, such as Arch's `wpewebkit` 2.54 without `libwpe` and `wpebackend-fdo`, is reported as not installed, and the page opens in WebKitGTK's window.

Closing the last WebKitGTK preview ends its web process, but its network process (about 40 MB) lives until Avala exits: `Avalonia.Controls.WebView` 12.1's `GtkWebViewAdapter` creates each preview's private context with `webkit_web_context_new_ephemeral` and destroys only the web view when it is disposed, never releasing its reference to that context, and the network process belongs to the context. Neither `WebViewEnvironmentRequestedEventArgs` nor the surface's platform handle gives Avala the context to release, and releasing it behind the adapter would free it twice as soon as a later adapter releases it, so this waits on the adapter; sharing WebKit's default context instead would keep one network process too, and would give previews persistent storage.

The Workbench draws the job's page as regions, `WorkbenchRegions`, beside the shell's: the job's header holds the Running chip, whose dot pings once as it appears, and Run, the conversation a chip of its own while the pane is closed, and the preview sits right of the conversation at 45% of it by default, resized by dragging its edge between 25% and 70%, remembered in `layout.json`, reset by a double-click, and hidden in focus mode. A server that a selected job starts opens the pane by itself, once for that job and port, so a person who closes it is not interrupted again by the same server, and a server already running when its job is selected waits for the chip. A link in a reply to a loopback address that one of the selected job's servers answers, on its lease or a port it listens on, opens in the pane instead of the browser: the Workbench sends the SDK's `LocalPageRequested` UI message and opens the browser only when no pane shows the page.

### Motion and layout

Motion is opt-in. An element animates only through `Motion.Enter`, `Motion.Loop`, `Motion.When` and `Motion.Swap`, which replays a short fade and scale whenever its bound value changes but not when it is first set, and they check reduced motion themselves; a loop runs only while its element and every ancestor are visible, and a fold's one-shot animations finish even while hidden, since a paused animation keeps Avalonia's 60 Hz animation clock awake. The theme holds no style that matches every visual, because Avalonia attaches such a style to each visual it builds and every screen paid for it.

Pages and the selected job's conversation appear on a **stage**: the click's own change, such as the sidebar highlight and the job's header, paints first; the new view is built at background priority while the current one stays on screen, and once the new view is laid out the two cross-fade in 240 ms with a slight rise and scale on a settling curve, started on a fresh frame so a slow build never eats the fade; under reduced motion the swap is instant. Page views stay alive between visits and the four most recently viewed conversations keep their view models and views, so switching back is instant, and entrances inside content being laid out hold still so only later arrivals move.

The agent tree moves on its own frame loop rather than on styles. `AgentTreePanel` keeps every card's place by its item, so a refresh that moves a card is told apart from one that adds or removes it: a card that moves keeps its final bounds for layout and hit testing and glides there through a render offset in 240 ms on a gentle out curve; a new branch's line draws from its parent's joint, along the bar, down to the card in 220 ms, and the card fades in and rises 6 px into place over 260 ms once the line is most of the way; a branch that folds or leaves shrinks toward its parent's joint and fades in 220 ms while its line retracts. The pure `AgentTreeLayout.Connect` draws the lines of any moment from the cards' shown places and how far each new line has grown. Working lines stream a slow dash and waiting ones breathe between 55% and full strength over 2.8 s; both run only while such a line is shown and the panel is visible, the clock rests otherwise, and their pens are made once per phase and theme so a streaming frame allocates nothing. A card's border eases to its state's color in 220 ms and a settled card dims to its opacity in 320 ms, and its state chip swaps its mark with `Motion.Swap`. A pane resized or first shown lays its cards out at once, and under reduced motion everything lands in place immediately, which the headless screenshots rely on.

The conversation is virtualized by a timeline panel: it opens at its newest screenful without building its first entries, builds older entries as the reader scrolls up, where they hold still, and a newly opened conversation fills its entries in one change. The panel remembers each entry's measured height for the column's width, estimates an entry not yet built from the heights measured for its kind and from its text length, which messages, prompts and interjections give through `ITextSized`, and builds the screenful above and below at idle priority, so the scrollbar holds steady and a first scroll finds its entries ready; what the reader sees stays in place while entries above settle. While a reply streams, each settled block becomes its own Markdown view and is never parsed or drawn again, only the growing last block is; Select All and Copy span the blocks, and once the reply ends it becomes one document again, so a drag selection can cross its blocks. A conversation shares one set of Markdown styles instead of loading them per message. Each inspector section shows as soon as its own facts are read, with a quiet bar that appears only if the read takes longer than 150 ms, and pages update their rows in place, as the Usage page's connections do, instead of rebuilding them on every refresh.

The window keeps its layout in `layout.json` next to `appearance.json`: the sidebar collapses from the window controls or Ctrl/⌘+\ and below 1,000 px, and its width, 260 px by default, follows a drag of its edge between 200 and 400 px, is remembered once the drag ends and returns to 260 px on a double-click; rows that would clip shorten or drop their secondary facts through container queries. Focus mode is only a shortcut, Ctrl/⌘+Shift+F: it hides the sidebar, the inspector, the window controls and the page and job headers, widens the reading column as Wide does and shows a hint that fades out; Esc or the same shortcut leaves it. The reading column grows with the window, further when Appearance sets the reading width to Wide.

### Personal details

Personal details are hidden by default, so a screen can be recorded or shared as it is. A view model never exposes a person's email, login, account name, organization id or home-folder path as plain text: it exposes a `Personal` value of the shared components, which knows its kind and masks it by one rule per kind (`r•••••@g••••.com`, `oc•••••`, `D••••• M•••••`, `3f2a•••••`, `~/…`), or a `PersonalPhrase` for a sentence that holds one. Views show them through `PersonalDetails.Text`, and free text that may mention them, such as a tool line, a permission target or a repository path, through `PersonalDetails.Scrubbed`.

A notice or error that names one does the same: a sentence that holds a known folder or login, such as an unopened log folder, a created or cloned repository or a published origin, is a `PersonalPhrase`, and one that may hold a path, such as a file the platform would not open or what a command writes, is scrubbed; both follow the inherited `PersonalDetails.AreHidden` of the window, which the appearance sets, so a change applies live everywhere, popups included. The switch is "Hide personal details" in Settings, Appearance, kept in `appearance.json` as `hidePersonalDetails`, with an eye in the Accounts header for the same setting; a copied or exported conversation is scrubbed the same way while it is on. Connection names are chosen by the person and stay as they are. An architecture rule rejects a view model interface whose text property is named after an email, a login, an account, an organization, a user name or an owner.

## Performance practices

Each practice below is described where it applies; this is the list to keep in mind for a change.

- **Nothing heavy on the UI thread.** The runtime, its router and the startup tasks run on the thread pool; database work, SVG parsing, image decoding and code tokenizing run off the UI thread, and only what changes the screen is marshalled to it ([startup](#startup-and-shutdown), [persistence](#persistence), [the conversation](#the-conversation), [canvases](#canvases)).
- **Show first, refine later.** A code block shows plain text before it is colored, a canvas keeps its previous drawing until the new one is drawn, an inspector section shows as soon as its own facts are read, and a stage paints the click's own change before it builds the next view ([the conversation](#the-conversation), [motion and layout](#motion-and-layout)).
- **Bounded caches, released when unseen.** Parsed SVG pictures and decoded images are kept up to 64 MB each and code colors up to 8 MB; a picture is held only while its row is realized or its sheet is open.
- **Build only what is seen.** The conversation is virtualized, a streaming reply re-parses only its last block, page views and the four most recent conversations are kept alive, and rows update in place instead of being rebuilt.
- **Motion costs nothing when idle.** Animations are opt-in, run only while visible and respect reduced motion; no style matches every visual ([motion and layout](#motion-and-layout)).
- **Measure, then change.** Every optimization and workaround names what was measured, such as the 545 ms to 95 ms of a code block, and the packages are precompiled with ReadyToRun for a faster first frame ([Releasing](release.md#the-packages)).

### Platform workarounds

Each workaround answers a problem that was reproduced and measured, and goes when its cause is fixed.

| Workaround | Problem | Measured | Goes when |
| --- | --- | --- | --- |
| Wayland backend (`DesktopSession`) | Avalonia draws through X11 on Linux by default. Under a Wayland compositor at a fractional scale (1.6 on Hyprland), XWayland renders the window at scale 1 and the compositor stretches it, so text is blurry. The X11 alternative (`xwayland:force_zero_scaling` with Avalonia's own scale) misplaces clicks. | WebKitGTK without its DMA-BUF renderer (`NativeSurfaces`) | Under native Wayland, WebKitGTK only opens the preview in a window of its own through XWayland, and its DMA-BUF renderer fails to allocate its GBM buffers there ("Failed to create GBM buffer"), so the window stays blank. On Linux, when the variable is unset, the Preview plugin sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` as it registers, before WebKit loads. | 2026-10-12, Hyprland 0.56 on Arch, WebKitGTK 2.54.1: a blank preview window, the page drawn with the variable set | WebKitGTK allocates its buffers under XWayland, or WPE WebKit embeds the preview |

## Testing and quality

### The simulator and recordings

Everything Avala does is proven through the **simulator**, a provider plugin that plays scripted Claude Code sessions through the same public contracts as a real provider, without a model and without tokens. Its scenarios are declarative data: reasoning, streamed replies, real file edits, commands with real child processes, permission requests, forms, plan approvals, usage and limits, canvases, delegation and resumed conversations. It also registers a second simulated harness, so behavior across harnesses runs without a real one.

The **Recording** plugin decorates every provider and, when enabled, records each session as a file the simulator replays. Recordings committed under `tests/recordings` with their expected outcomes are regression tests, and the screenshots in the README are taken from the real application driven headless by the simulator. A Claude Code connection whose settings name a `transcripts` folder also taps the CLI's own stream into that folder, in the shape the Claude Code replays under `tests/transcripts/claude-code` use; `scripts/anonymize-transcript.cs` turns such a real session into a fixture there, with its folders as placeholders and the account, the person's skills and plugins and their home folder taken out.

The simulator, the simulated forge and Recording exist only to develop and test Avala. Their projects declare `<AvalaDevelopmentOnly>true</AvalaDevelopmentOnly>`, so `dotnet build` still copies them to `artifacts/plugins` but no package holds them; see [the production plugin set](release.md#the-production-plugin-set). Claude Code is the only harness Avala officially supports.

### Tests

- One test per behavior, named after what it proves. Unit tests by default, with a fake for every port the component uses; only a component's own integration test uses its real dependency, such as git, SQLite or a process. Behavior across modules is proven through the simulator, never a real agent.
- Views are tested headless: every component has scripted acceptance tests that drive it as a user would, and leak tests check that a surface's managed memory does not keep growing across thirty cycles: they take the floor of the managed memory measured after each cycle in each third of them and fail only when it rises from the first third to the second and again to the last, so a cache that fills and empties, as image decoding does on macOS, or settles once at a higher level passes, while memory that keeps growing fails with every reading.
- Host scenarios run Workspaces in memory: `InMemoryWorkspacesPlugin` in `tests/Avala.Workspaces.Testing` replaces the module behind its contracts, keeping commits, checkpoints, diffs, merges and base files in memory while worktrees stay real folders the simulated agent writes in. One conformance check, `WorkspaceConformance`, runs the same lifecycle against the module with git and against the fake, so the two cannot drift. A scenario that proves git's own behavior, such as pushing to a forge, merging into a checkout or cloning, is marked `[UsesRealGit]` on its class or method and runs the real module; a test that runs git on an in-memory repository fails, saying so.
- No test waits on time: it awaits the event that states the thing happened, and a fake clock replaces the views' clock.
- A host test's `EventWatch` gives up only when the application has gone quiet: no awaited event, no job step and no process of its own, such as git preparing a worktree or a check running, for 30 seconds. A running process counts as work, so a slow machine makes a test slower instead of failing it, and five minutes is the most any single wait takes, so a hung process still fails the test with what it last saw.
- Every simulated scenario checks the lifecycle invariants when it ends, before Avala stops, once its event bus has delivered and every job's queue has run what it was given (`InvariantCheck` and `Invariants` in the host tests, reported by the assembly's `InvariantsKept` attribute beside the test's own result): a job fails exactly when it records why, its hold agrees with its status, it has ended exactly when approved, discarded or failed, only the last attempt of a working job is underway, an ended job stops its session and leaves no process tree in its worktree, no child outlives its parent's end, no turn stays open once its session ended, no item stays open once its turn ended, a session with a live turn or background work is never rested, usage is never negative, and every message reaches the agent once or is reported undelivered. Before a restart only the invariants that hold at every instant are checked, without waiting for Avala to go quiet, so a restart still happens where its test put it and a gate that holds a handler until shutdown cannot hang it. A test about anything else still catches a violation, and `BrokenInvariantsAsync` checks them mid-scenario, as `LongScenarioTests` does after every step of a job that delegates, rests, runs out of two windows, is woken by a failing CI on its pull request and is handed off, over hours of fake time. A harness's own sub-agent is an item of its parent's turn, so it ends in a terminal state when its item closes; a delegated child is a job and ends with its parent. Worktrees are not checked, since an approved job's worktree is kept on purpose, and neither are processes view models start, since a host test never closes its window. A message is told apart from an identical one by the `MessageId` its `JobMessage` carries through Jobs into the `UserTurn` the harness receives, and messages merged into one turn carry all their ids; `MessageLedger` records what `IJobMessages` and `IJobs`, `ContinueOnAsync` included, accepted or refused and which ids a harness session accepted, and the Workbench's queue says through the UI message `QueuedMessageChanged` when it queues, takes, withdraws, returns or drops a message. A message accepted that reached the agent twice or never, unless its job failed on the attempt it was given to or the one that attempt started, a message refused that reached it anyway, a message taken from the queue that no job accepted, and a message left queued for a discarded or failed job break the invariant. One ledger lives as long as its simulated run, across restarts. The job's draft keeps every message waiting in the queue and every message that came back, so neither is lost to a restart or a crash: a message still queued when Avala stopped comes back at startup, and a queued message a job can no longer take comes back at once, marked in the sidebar; the composer puts it in front of whatever the person is typing and says why; a message sent to a job the queue saw end is refused instead of queued. A message, an answer, an interrupt or a remote-control change Claude Code cannot write to its CLI is refused as `SessionClosed` rather than reported done; when a message to a job's open session is refused that way, Jobs holds the job as `SessionLost` and continues it in a resumed session with the same message, and if that fails too it refuses the message so the person keeps it, never failing the job; and the simulator, as the CLI does, starts the next turn with a message queued after a finished turn last listened. A brief that repeats what the person sent carries no id, since it is context rather than the message.
- The job's lifecycle also has a model-based test, `JobModelTests`: seeded sequences of commands are played against the `Job` aggregate and a small reference model written from the design rather than from the code, which must agree on every answer and state; every batch of fifty seeds must reach every state and accept every command, and a disagreement names its seed and the commands played.
- The lifecycle [diagrams](diagrams/) are compared with the state machines on every run; `AVALA_UPDATE_DIAGRAMS=1` rewrites them.

[Contributing](../CONTRIBUTING.md#tests) has the practical side.

### Quality gates

The rules are code, and a failing rule explains itself.

- **Architecture tests** in `tests/Avala.ArchitectureTests` enforce the module boundaries, the layer map, the domain's purity, the view rules, the absence of comments, type and component size limits, the concurrency and timing rules, and that every script is C#. The one exception is the docs site's template in `src/Modules/Documentation/Avala.Documentation/SiteTemplate/public/`: the `<avala-c4>` player runs in the reader's browser, where only JavaScript runs, so that folder may hold `.js` files; they are embedded in the Documentation module and written into a repository's docs site by **Create site**, which puts them in `docs/template/public/`, the one other folder that may hold them, since Avala's own docs site is laid out the same way. Each rule runs against the production code, a compliant fixture module and a violating fixture module, so it can never pass vacuously.
- **Analyzers** run on every project as errors: banned symbols for blocking calls, timed waits and coordination primitives, the threading analyzers, SonarAnalyzer.CSharp and the .NET code metrics rules, with their limits in `SonarLint.xml` and `CodeMetricsConfig.txt`.
- **CI** builds and tests on Linux on every push to `main` and every pull request, running each test project once: the unit tests of `Avala.UnitTests.slnf` with coverage, then the architecture, documentation, integration and host tests of `Avala.SystemTests.slnf`. Windows and macOS build and test every night, on demand and before every release. CI uses only `dotnet` steps.

### Quality metrics

On every push to `main` and every pull request, CI also measures coverage, code metrics, technical debt and lines of code with open-source tools and no external service, and shows them in the run summary.

- **Coverage** comes from the unit tests, listed in `Avala.UnitTests.slnf`, collected on Linux.
- **Code metrics** are the maintainability index, cyclomatic complexity, class coupling and lines of every production assembly, type and member, computed by `scripts/code-metrics.cs`.
- **Lines of code** are physical lines of C# outside tests and generated code. They are compared with [T3 Code](https://github.com/pingdotgg/t3code), about 907,000 lines of non-test TypeScript at commit `a4c9494b0`, as a fixed yardstick: Avala aims for a better product in no more than 15% of that.

### Technical debt grade

`scripts/metrics.cs` rates four indicators from A to E, and the grade is the worst of the four:

| Indicator | A | B | C | D | E |
| --- | --- | --- | --- | --- | --- |
| Line coverage of the unit tests | ≥ 80% | ≥ 70% | ≥ 60% | ≥ 50% | < 50% |
| Mean maintainability index of the production methods | ≥ 80 | ≥ 70 | ≥ 60 | ≥ 50 | < 50 |
| Highest cyclomatic complexity of a production method | ≤ 10 | ≤ 15 | ≤ 20 | ≤ 25 | > 25 |
| Risk hotspots (CRAP score above 30) per 1,000 methods | ≤ 1 | ≤ 5 | ≤ 10 | ≤ 20 | > 20 |

On a push to `main`, the badges in the README are drawn by the same script and published on the `badges` branch.
